# Security Contract

This document defines the account model, permissions, authentication API, token lifecycle, CSRF integration and endpoint access rules for the [security epic (#33)](https://github.com/codeurjc-students/2026-Artseek/issues/33). It was written in [P3-SEC-01 (#34)](https://github.com/codeurjc-students/2026-Artseek/issues/34), which also implements user persistence. The remaining sub-issues implement this contract; any change to it must update this document in the same pull request.

## Accounts

**Implemented in #34.** A `User` is persisted in the `users` table. `user` is a reserved word in PostgreSQL, so it is not used as the table name.

| Attribute | Rules |
| --- | --- |
| `id` | Generated database identity. It is the JWT subject and the `requesterId` passed to commands and queries. |
| `username` | Trimmed, then lowercased with the root locale. It must be 3–30 characters from `a-z`, `0-9`, `.`, `_` and `-`. It is unique (`uk_users_username`) and public. |
| `email` | Trimmed and lowercased, at most 254 characters, in the form `local@domain.tld` with no whitespace or extra `@`. It is unique (`uk_users_email`) and private: it never appears in public DTOs. |
| `password_hash` | An encoded Argon2id hash; see [Password storage](#password-storage). It is never exposed. |
| `role` | `USER` or `ADMIN`, stored by name. |
| `created_at`, `updated_at` | UTC instants generated by the database (`current_timestamp`) on insert and on every update, through Hibernate `@CreationTimestamp` / `@UpdateTimestamp` with `SourceType.DB`. |

The `User` factories take primitive values and always build the `Username`, `Email` and `PasswordHash` value objects themselves, so every value object validates its input and no field can be left unset. Normalization happens when those value objects are built. Lookups and persisted values therefore always use the same form, and the plain database unique constraints are case-insensitive in practice. Two registrations that differ only in case or surrounding whitespace collide.

Validation failures raise domain exceptions under `domain/exceptions/user/`. Every domain validation exception, including the existing category ones, extends `domain/exceptions/DomainValidationException`, which exposes the rejected `field` and a fixed message. `InvalidPasswordHashException` deliberately does not keep the rejected value, because it could be a plaintext password passed by mistake.

The public representation is `UserDTO(id, username, role, createdAt)`. `role` is the public value (`"user"` or `"admin"`). `User.toString()` includes only the id, username and role, and `PasswordHash.toString()` prints `PasswordHash[PROTECTED]`.

## Permissions

| Principal | Persisted | Grants |
| --- | --- | --- |
| Anonymous | No | An unauthenticated state, not an account. Can call public endpoints only. |
| `USER` | Yes | The default for every new account. Can call authenticated endpoints and act on resources it owns. |
| `ADMIN` | Yes | Everything `USER` can do, plus restricted endpoints such as future shared-catalog writes. |

- `User.register(...)` always assigns `USER`. No request payload can choose a role: registration DTOs have no role field, and any unknown JSON fields are ignored, never mapped onto the entity (**Planned, #35**, covered by negative tests).
- `User.createAdministrator(...)` is the only way to create an administrator. Only trusted, non-public code may call it. No HTTP endpoint will. Once hashing exists (**Planned, #35**), a bootstrap step may create the initial administrator from environment-supplied credentials.
- Spring Security authorities are derived from the role as `ROLE_USER` and `ROLE_ADMIN` (**Planned, #35/#36**).

## Password storage

**Contract fixed in #34. Hashing and verification are planned for #35.**

- **Algorithm:** Argon2id, version 19 (0x13).
- **Salt:** A unique 16-byte salt per hash, generated with a cryptographically secure random generator.
- **Hash length:** 32 bytes.
- **Cost parameters:** Configured explicitly, never left to library defaults. The OWASP minimum baseline is `m=19456` KiB (19 MiB), `t=2`, `p=1`. Spring Security's `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()` uses 16 MiB of memory, which is **below** that baseline, so it must not be used unchanged.
- **Benchmarking (#35):** Measure hashing time on the development machine and on deployment-like hardware. Raise memory first, then iterations, while one hash stays at or below about 0.5 s and never goes below the baseline. Record the chosen values and measurements here.
- **Storage:** The single `password_hash` column holds the PHC string `$argon2id$v=19$m=<KiB>,t=<iterations>,p=<parallelism>$<base64 salt>$<base64 hash>`. It carries everything needed for verification and future rehashing: algorithm, version, cost parameters, salt and hash. The domain `PasswordHash` value object accepts only this format, so a plaintext password cannot be persisted, and it exposes the parsed metadata.
- **Rehashing:** After a successful login, if the stored parameters are weaker than the configured ones, the password is rehashed and saved through `User.changePasswordHash` (**Planned, #35**).
- **Plaintext:** Plaintext passwords exist only in the request being processed. They are never persisted, logged, echoed in errors or placed in DTO `toString()` output.

Password input rules for registration (**Planned, #35**): 12–128 characters, with no composition rules and no trimming. All Unicode characters are allowed. The upper bound limits hashing cost per request.

## Authentication API

**Planned, #35.** All endpoints live under `/api/v1/auth` and exchange JSON. Tokens are carried only in cookies and never appear in response bodies.

| Endpoint | Access | Request | Success | Errors |
| --- | --- | --- | --- | --- |
| `GET /csrf` | Public | — | `204`; sets the `XSRF-TOKEN` cookie | — |
| `POST /register` | Public, CSRF | `RegisterUserRequest(username, email, password)` | `201` with `UserDTO`; does not sign in | `400` validation, `409` duplicate |
| `POST /login` | Public, CSRF | `LoginRequest(identifier, password)` | `200` with `UserDTO`; sets the access and refresh cookies | `400` validation, `401` invalid credentials |
| `POST /refresh` | Refresh cookie, CSRF | — | `204`; rotates both cookies | `401` missing, invalid or expired refresh token |
| `POST /logout` | Public, CSRF | — | `204`; clears both cookies | — |
| `GET /me` | Authenticated | — | `200` with `UserDTO` | `401` |

- **Login identifier:** A value containing `@` is normalized as an `Email`. Anything else is normalized as a `Username`.
- **Login failures:** Every failure returns the same `401` body: unknown identifier, wrong password, or an identifier that cannot be normalized. When the account is unknown, a dummy hash is still verified, so response timing does not reveal whether the account exists.
- **Duplicate accounts:** Registration returns `409` with the conflicting field (`username` or `email`). This trades some account enumeration for usability; the abuse controls in #40 rate-limit registration. Pre-checks use `existsByUsername` and `existsByEmail`. When two registrations race, the database unique constraints decide, and the constraint names map to the same `409`.
- **Login result:** Login returns the authenticated user. Under the CQRS rule that commands return nothing, #35 decides whether login is modeled as a query or as a documented exception.

## JWT lifecycle

**Planned, #35.** Authentication is stateless. No server-side HTTP session is created (`SessionCreationPolicy.STATELESS`), and every request is authenticated from its token.

| Aspect | Contract |
| --- | --- |
| Format and signing | JWS signed with HS256 using a key of at least 256 bits from secure configuration (`JWT_SIGNING_KEY`). It is never committed or logged. Validation pins the algorithm and rejects `none` and any other algorithm. |
| Access-token claims | `iss=artseek`, `aud=artseek-api`, `sub=<user id>`, `role`, `iat`, `exp`, `jti`, `typ=access`. |
| Validation | Signature, `iss`, `aud`, `typ`, `exp` and `iat`, with 30 s of allowed clock skew. The account is not reloaded on every request, so role changes take effect at the next refresh. |
| Access-token transport | Cookie `artseek_access`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api`, `Max-Age` equal to the token lifetime. Never stored in `localStorage` or `sessionStorage` and never readable by JavaScript. |
| Access-token lifetime | 15 minutes. |
| Refresh token | A separate JWT with `typ=refresh` and a 7-day lifetime, in cookie `artseek_refresh`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/v1/auth/refresh`. It is only sent to the refresh endpoint and only accepted there. |
| Renewal | `POST /refresh` validates the refresh token, reloads the user and issues a new access and refresh pair (rotation). The frontend calls it once after a `401` and repeats the original request; a second `401` means the user must sign in again (#37). |
| Logout | `POST /logout` expires both cookies in the browser. **This is not server-side revocation.** A copied token remains cryptographically valid until it expires: up to 15 minutes for access tokens and 7 days for refresh tokens. Server-side revocation (a per-user token version or a deny-list) is out of scope for this epic. |
| Expiry | An expired, tampered, wrong-type or wrong-audience token never authenticates a request. Protected endpoints answer `401`. |

## CSRF protection

**Planned, #35 (auth endpoints) and #38 (application-wide hardening).**

Authentication cookies are sent automatically by the browser, so unsafe requests need CSRF protection even though there is no session. Spring Security's `CookieCsrfTokenRepository` keeps the token in a cookie instead of a session, which stays compatible with stateless authentication.

1. **Acquire:** Call `GET /api/v1/auth/csrf`. The response sets the `XSRF-TOKEN` cookie, which is readable by JavaScript and has `Secure`, `SameSite=Strict` and `Path=/`.
2. **Submit:** Every `POST`, `PUT`, `PATCH` and `DELETE` sends the cookie value in the `X-XSRF-TOKEN` header. The shared frontend `apiRequest` wrapper adds the header (#37).
3. **Rotate:** Fetch a new token after login and logout.

A missing or mismatched token returns `403` with code `csrf_invalid`. Login and registration also require the token, to prevent login CSRF. `GET`, `HEAD` and `OPTIONS` requests must not change state.

## Error responses

**Planned, #35/#36.** Failures return JSON from a shared `ApiErrorDTO(status, code, message, fieldErrors)` in `infrastructure/api/`, built by a single `@RestControllerAdvice`. Bodies never include stack traces, tokens, hashes, passwords or internal class names:

```json
{ "status": 401, "code": "unauthenticated", "message": "Authentication is required." }
```

| Status | `code` | When |
| --- | --- | --- |
| `400` | `validation_failed` | Any `DomainValidationException`, through one handler, plus request-level validation. Includes `fieldErrors: [{ "field": "username", "message": "..." }]` from the exception's `getField()` and `MESSAGE`. A password value is never echoed. Exceptions are: at login, invalid identifiers map to `401 invalid_credentials`; and `InvalidPasswordHashException` can only come from a server-side encoder fault, so it maps to `500`. |
| `401` | `unauthenticated` | Missing, invalid, expired or tampered access token on a protected endpoint. |
| `401` | `invalid_credentials` | Failed login, with an identical body for every cause. |
| `403` | `forbidden` | Authenticated, but the role or ownership check fails. |
| `403` | `csrf_invalid` | Missing or invalid CSRF token on an unsafe request. |
| `409` | `account_conflict` | Duplicate username or email during registration, with `field`. |
| `429` | `too_many_requests` | Rate limit on login or registration (#40). |

Existing category behavior is unchanged: an unsupported category type still returns `400` with an empty body until a shared error handler is introduced.

## Access matrix

**Planned, #35/#36.** The security filter chain lists every route explicitly and ends with `anyRequest().denyAll()`. A newly added controller is therefore unreachable until its access rule is added here and to `SecurityConfig` in the same pull request.

| Endpoint | Anonymous | `USER` | `ADMIN` | Notes |
| --- | --- | --- | --- | --- |
| `GET /api/health` | ✅ | ✅ | ✅ | Existing; must stay public. |
| `GET /api/v1/categories/types/used` | ✅ | ✅ | ✅ | Existing; must stay public. |
| `GET /api/v1/categories/{type}` | ✅ | ✅ | ✅ | Existing; must stay public. |
| `GET /api/v1/auth/csrf` | ✅ | ✅ | ✅ | |
| `POST /api/v1/auth/register` | ✅ | ✅ | ✅ | CSRF required. The resulting account is always `USER`. |
| `POST /api/v1/auth/login` | ✅ | ✅ | ✅ | CSRF required. |
| `POST /api/v1/auth/refresh` | Refresh cookie | Refresh cookie | Refresh cookie | CSRF required. |
| `POST /api/v1/auth/logout` | ✅ | ✅ | ✅ | CSRF required. |
| `GET /api/v1/auth/me` | `401` | ✅ | ✅ | |
| `/v3/api-docs/**`, `/swagger-ui/**` | ✅ (local) | ✅ (local) | ✅ (local) | Public while springdoc is enabled; exposure in deployment is decided in #38. |
| Future category writes (`POST`/`PUT`/`DELETE /api/v1/categories/**`) | `401` | `403` | ✅ | Categories are a shared catalog. |
| Any other route | `401` | `403` | `403` | Denied by default. |

`OPTIONS` preflight requests are handled by the CORS configuration, which stays restricted to the configured frontend origin and allows credentials (#35/#38).

## Ownership

Role checks run in the security filter chain. Ownership checks run in the application and domain layers.

- **How:** A controller passes the authenticated principal's id as `requesterId` in the command or query. The handler loads the resource and asks the domain, for example `portfolio.isOwnedBy(requesterId)`. Failure raises a domain exception that the API maps to `403`. Handlers never read the security context.
- **Current resources:** None are user-owned. `Category` is a shared catalog entry with no owner, and none will be added; its future writes are an `ADMIN` role check, not an ownership check.
- **Current account self-access:** `GET /api/v1/auth/me` returns only the caller's own account, resolved from the token subject. No endpoint accepts another user's id for account data.

Future dependencies, tracked outside this epic:

| Resource | Issue | Ownership rule to implement |
| --- | --- | --- |
| Profile and private account details, including the display name | [P3-PRF-01 (#42)](https://github.com/codeurjc-students/2026-Artseek/issues/42) | Only the account itself may read private details or change its profile; public profile fields stay readable. |
| Artist activation and portfolio | [P3-ART-01 (#49)](https://github.com/codeurjc-students/2026-Artseek/issues/49) | Only the owning artist may modify their portfolio and artworks. Whether administrators may moderate others' content is decided in that issue. |

## Logging and secrets

- **Never log:** passwords, password hashes, tokens, cookie values, CSRF tokens or signing keys. Domain objects that hold credentials redact them in `toString()`.
- **Security events (#40):** registration, login success and failure, refresh failure, logout, `401` and `403` outcomes. Each event logs the normalized username or user id, the client address and the outcome, and nothing else from the request.
- **Secrets:** Signing keys, database credentials and certificate private keys come from environment variables or untracked files and are never committed. Local development uses documented placeholders (#35, #39).
